There is no API key to request and no token to send. These routes serve the Hexkit
app, and they authorise requests by **where they came from**, not by who sent them.

If you're [self-hosting](/self-hosting), this page is the part that decides whether
your deployment works.

## Origin allowlisting

Every route checks the `Origin` header:

- An origin on the allowlist is served
- An origin **not** on the allowlist gets `403 Origin not allowed`
- A request with **no** `Origin` header is served

That last rule is deliberate. Browsers omit `Origin` on many same-origin requests,
particularly `GET`s, so rejecting header-less requests would break the app against
itself.

Set the allowlist with a comma-separated list:

```bash
ALLOWED_ORIGINS=https://yourdomain.com,https://preview.yourdomain.com
```

`localhost` origins are always accepted, so local development works without
configuration.

<Note>
  Because header-less requests pass, these routes are reachable by anything that
  isn't a browser. The upstreams they front are either keyless or rate-limited, so
  the exposure is your own serverless quota rather than your credentials. The intents
  proxy adds a per-IP rate limit of 120 requests per minute as friction — it is not
  authentication.
</Note>

## Server-side credentials

Keys live in the deployment environment and are attached by the route handler.

| Variable | Used by | Notes |
|---|---|---|
| `LIFI_API_KEY` | `/api/lifi-earn`, `/api/lifi-composer` | Without it, both return `500 LIFI_API_KEY not configured` |
| `GEMINI_API_KEY` | `/api/llm-recommend` | Without it, the concierge falls back to rules-based suggestions |
| `EDB_BRIDGE_URL` + `EDB_API_KEY` | `/api/edb/*` | **Both** required, or every call returns `503 bridge_not_configured` |
| `ETHERSCAN_API_KEY` | `/api/explorer/etherscan` | Users may supply a personal key instead |

Nothing prefixed `VITE_` is a secret — those are compiled into the browser bundle and
are readable by anyone.

## The PROXY_SECRET trap

`PROXY_SECRET` switches the routes from origin checks to requiring an
`x-proxy-secret` header.

<Warning>
  **Do not set this on a browser-facing deployment.** The web client never sends that
  header — `proxyHeaders()` in the app deliberately returns an empty object — so
  setting `PROXY_SECRET` makes every proxied call return `403`. Vault data, quotes,
  order status, and AI recommendations all stop working at once.

  It is only useful if you are calling these routes from your own server and can set
  the header yourself.
</Warning>

This is worth checking first if a fresh deployment returns `403` everywhere.

## CORS

Successful responses echo the allowed origin back in
`Access-Control-Allow-Origin`. Preflight `OPTIONS` requests are answered with the
permitted methods and headers.

The EDB proxy keeps its own allowlist, extendable with
`EDB_CORS_ALLOWED_ORIGINS`, because it is often pointed at a bridge running
somewhere other than the app.

## Diagnosing a failure

| Response | Cause | Fix |
|---|---|---|
| `403 Forbidden` | `PROXY_SECRET` is set | Unset it |
| `403 Origin not allowed` | Origin missing from the allowlist | Add it to `ALLOWED_ORIGINS` |
| `500 LIFI_API_KEY not configured` | No LI.FI key | Set `LIFI_API_KEY` |
| `503 bridge_not_configured` | EDB URL or key missing | Set both `EDB_BRIDGE_URL` and `EDB_API_KEY` |
| `405 Method not allowed` | Wrong verb | The data proxies are read-only |
| `429 rate_limited` | Over 120 requests/minute | Wait, or check for a polling loop |
